# Update Checker (v0.5.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** lolPing checks GitHub for new releases, tells the user once per version, and updates on a click: a silent install and relaunch on Windows, and a verified DMG opened for a drag-to-Applications on a Mac.

**Architecture:**
- An `Updater` in the main process owns the schedule (10 s, then 6 h), the `UpdateState` and the notify-once rule.
- It drives an `UpdateBackend`:
  - `WinBackend` wraps electron-updater (GitHub provider, `autoDownload` off);
  - `MacBackend` uses GitHub's `releases/latest` API, streams the DMG while hashing it against GitHub's SHA-256 asset digest, then opens it.
- The tray, the About card and an overlay toast render from `UpdateState`.
- Packaging gains a `publish` entry, so electron-builder writes `latest.yml`; the release workflow uploads it with the blockmap.

**Tech Stack:** Electron 44 main process, TypeScript 5.9, electron-updater 6.x (bundled into `out/main`), electron-builder 26, React 19 + Fluent UI 9, vitest 5 with fake timers.

**Spec:** `docs/superpowers/specs/2026-10-06-updater-design.md` (§ numbers below refer to it).

## Global Constraints

- **Branch and commits:**
  - Continue on branch `v0.5` after the emotes M1 plan.
  - **No commits until the end.** Tasks end with a checkpoint. After the user's go-ahead (Task 6), this plan lands as **one commit**.
  - Tag and push only when the user asks.
  - No Claude or AI attribution anywhere.
- **Dependencies:** `electron-updater` as a **devDependency at an exact version** (the latest 6.x when installed), so electron-vite bundles it. The installer ships only `out/**`, so nothing may be left as a runtime `require('electron-updater')`.
- **Spec constants (exact):**
  - first automatic check 10 s after launch, then every 6 h;
  - GitHub API timeout 15 s, `User-Agent: lolPing/{version}`, `Accept: application/vnd.github+json`;
  - Mac asset name `lolPing-{x.y.z}-arm64.dmg`, digest `sha256:<64 hex>`, download to `<Downloads>/<name>.part` then rename;
  - release notes URL on Windows `https://github.com/darrenprx/lolPing/releases/tag/v{version}`;
  - `quitAndInstall(true, true)`.
- **Test override:** `LOLPING_UPDATE_TEST_URL` is honoured in dev and packaged builds (§5.1, §5.2). Without it, dev builds create no Updater.
- **Strings:** every new string in en and zh-CN in `src/shared/i18n.ts`.
- **Version:** bump `package.json` (and the two version fields in `package-lock.json`) with one-line edits, not `npm version`, which reformats the compact `package.json`.
- **Dev runs:** back up `%APPDATA%\lolPing\` first and restore it afterwards. Check the running app over CDP. Ask the user before installing any test build: they may have a real lolPing installed.
- **Style:** match the surrounding code (EventEmitter + typed events, injected dependencies for tests, as in `roomManager.ts` and `inputBridge.ts`).

## Review Focus

1. **Clicking Update twice, or Check for updates during a download:** Expected: one download, and the check is ignored. → Task 1 test `ignores checks and repeat starts while downloading`.
2. **The machine sleeps for a day, or GitHub hangs for minutes:** checks must never pile up or run in a burst. Expected: the next check is scheduled only after the previous one finishes. → Task 1 test `checks never overlap or pile up`.
3. **A Downloads folder that already holds `lolPing-x-arm64.dmg`, maybe half-written, from an earlier try:** Expected: the new verified file replaces it, and a stale `.part` is overwritten. → Task 2 test `replaces an earlier file and a stale .part`.
4. **The GitHub API returns HTML, or JSON without the expected fields (a captive portal or rate-limit page):** Expected: a failed check (silent when automatic), never a crash or a bogus "update available". → Task 2 test `treats non-JSON and missing fields as a failed check`.
5. **Quitting lolPing during a download:** Expected: it quits normally, and the `.part` file is deleted or left unused, never renamed. → Task 2 test `an aborted download never renames`; Task 1 test `stop() aborts a running download`.

```ts
export interface UpdateInfo { version: string; notesUrl: string }
export interface UpdateBackend {
  check(): Promise<UpdateInfo | null>;
  download(info: UpdateInfo, onProgress: (percent: number) => void, signal: AbortSignal): Promise<void>;
  install(info: UpdateInfo): Promise<void>;
}
export interface UpdaterDeps {
  backend: UpdateBackend;
  now(): number;
  autoCheck(): boolean;
  notifiedVersion(): string | null;
  setNotifiedVersion(v: string): void;
  /** Error text for the UI, already translated. */
  errorText(kind: 'check' | 'download' | 'damaged' | 'install', reason: string): string;
}
export const FIRST_CHECK_MS = 10_000, CHECK_INTERVAL_MS = 6 * 60 * 60 * 1000;
/** Thrown by a backend when the file doesn't match its published hash, or has none (Mac). */
export class DamagedDownloadError extends Error {}
export class Updater extends EventEmitter { // events: 'state' (UpdateState), 'notify' (version), 'installing' (version)
  constructor(deps: UpdaterDeps);
  get state(): UpdateState;
  start(): void;                         // schedules the first automatic check if autoCheck()
  setAutoCheck(on: boolean): void;       // starts or stops the schedule
  check(manual: boolean): Promise<void>;
  startUpdate(): Promise<void>;          // only from 'available' or a 'download' error
  stop(): void;                          // clears timers and aborts a download
}
```
- Settings gain `autoUpdateCheck: boolean` (default `true`) and `updateNotifiedVersion: string | null` (default `null`; anything that isn't `x.y.z` → `null`).
